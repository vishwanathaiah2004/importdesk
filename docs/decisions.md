# Design decisions and assumptions

A running log. Each entry feeds the Technical Design Document.
Assumptions are labelled **[A]** because the brief asks for every assumption to be marked.

## Stack

- **Single Next.js codebase (UI + route handlers).** One deployable, one language, no separate API service to keep in sync. The brief's core build fits in 6–8 screens, so a second backend would add deployment work without adding capability.
- **PostgreSQL.** Shipments, documents, fields, checks and corrections are relational. Foreign keys, unique constraints and transactions keep review state consistent when a correction re-runs cross-checks.
- **Supabase, Mumbai region.** The brief requires India hosting for confidential client prices. Database and file storage sit in the same region.
- **Prisma 6 (pinned).** Typed queries and versioned migrations the reviewer can read in `prisma/migrations`.

## Data model

- **`Decimal` for quantities, prices and amounts.** Floats give results like 16319.999…, which would break the invoice-total check (2,400 × USD 6.80 must equal exactly 16,320.00).
- **Every `ExtractedField` stores `confidence`, `sourceSnippet`, `sourcePage` and `status`.** This is what powers "low-confidence fields highlighted" and "must be confirmed by a person".
- **`FieldCorrection` keeps old and new values.** The accuracy report per field and per supplier is computed from it.
- **`CrossCheck.result` includes `NOT_CHECKED`.** A missing document or value is never a pass, and it blocks export.
- **`Shipment.version`.** Optimistic concurrency, so two executives editing the same shipment cannot silently overwrite each other.
- **[A] One document of each type per shipment** (`@@unique([shipmentId, type])`). Uploading again replaces the earlier file.
- **Rust-free Prisma client (`engineType = "client"`) with the `pg` driver adapter.** No query-engine binary to bundle, so serverless deploys are smaller and start faster.

## Sign-in and roles

- **Email + password, bcrypt-hashed; session in a signed, httpOnly JWT cookie (8 hours).** No third-party auth service is needed for two internal roles.
- **The token is only an identity.** Every request reloads the user from the database, so a changed role applies immediately.
- **Authorisation lives on the server.** `authorize(permission)` runs in every server action and route handler. The proxy only redirects signed-out visitors; hiding a button is never the protection.
- **One permission matrix** (`src/lib/auth/permissions.ts`), unit-tested.
- **[A] Roles from the brief:** executives upload, review and correct; the manager also approves, overrides failed checks and views the audit log.
- **Login errors don't reveal whether an email exists**, and the `next` redirect only follows internal paths (no open redirect).
- **[A] Demo credentials are shown on the login page** because this is a reviewer demo with synthetic data. A production build would remove that panel.

## UI foundation

- **Calm palette with three meaningful status colours:** amber = needs a person, red = mismatch, green = cleared. Used the same way on every screen.
- **Geist Sans for text, Geist Mono with tabular figures for extracted values**, so numbers line up for comparison. Fonts are self-hosted (no build-time call to Google Fonts).
- **Light theme only** for a screen used all day; no dark mode in this build.
- **Pages render per request** (`cacheComponents: false`) because review state changes with every click.

## Sample data

- **Seeded shipments arrive already extracted** (`modelName = "seeded extraction"`), so the reviewer sees populated screens at once. Live upload + AI extraction works for any new shipment.
- **SHP-24811 and SHP-24812 come from the brief's sample data.** [A] SHP-24813 (clean, already reviewed) and SHP-24814 (unreadable B/L) are added to show the happy path and manual entry.
- **The documents are real PDFs** generated by `prisma/samples/render.ts`, so the review screen shows an actual document beside the fields. The same PDFs are in `samples/` for manual upload.
- **SHP-24811 includes a simulated AI misread**: one digit of the B/L container number, at low confidence. It shows why a person confirms uncertain fields.
- [A] Company names follow the brief's anonymised style (Company B, C…). Importers are fictional.

## Data model changes

- **Line items and containers are stored as `ExtractedField` rows** (`line.1.quantity`, `container.1`), not separate tables. Every extracted value, header or line, then has the same lifecycle: confidence, source snippet, review status and correction history. One review code path instead of three.
- **Field definitions live in one file** (`src/lib/fields.ts`). The AI prompt, review screen, validation and export all read from it.
- **Uploaded files are stored in a separate `DocumentBlob` table** so listing documents never loads file bytes. [A] For the prototype, files live in Postgres in the Mumbai region; production would move them to private object storage in the same region.

## Deployment

- **Vercel with functions pinned to Mumbai (`bom1`) and Supabase Postgres in Mumbai (`ap-south-1`).** The brief requires India hosting for confidential client prices. The AI API is the one part not pinned to India; the TDD states that plainly.
- **Migrations run from a developer machine** (`npm run db:deploy`), not during the Vercel build, so a failed build cannot leave the schema half-migrated.
- **Security headers on every response:** `nosniff`, `SAMEORIGIN` framing (the review screen previews documents in an iframe on our own origin), a strict referrer policy, and no camera, microphone or location access.

## Upload and documents

- **Files are identified by their first bytes** (PDF, PNG, JPEG, WebP signatures), never by the file name or the browser's Content-Type. A renamed HTML or EXE file is rejected.
- **4 MB per file**, under Vercel's 4.5 MB request limit. [A] Scans and phone photos of trade documents fit comfortably.
- **Documents are served only through an authenticated route** (`/api/documents/[id]/file`) with `Cache-Control: private, no-store`. There are no public file URLs.
- **One workspace screen per shipment:** document tabs on top, the original document on the left, details on the right. The active tab is in the URL (`?doc=INVOICE`), so a link opens exactly that view.
- **Replacing a document asks for confirmation inline** and explains that its extracted fields and review work will be discarded.
- **Any change to a shipment's content withdraws an earlier approval** (`refreshShipment(..., { contentChanged: true })`). The manager approved what they saw, not what came after.
- **Upload progress uses XHR**, because `fetch` cannot report upload progress.

## AI extraction

- **Rule: the AI suggests, deterministic code validates, a person confirms.** Nothing the model says is trusted on its own.
- **One model call per document**, with the file sent inline and a strict JSON schema. The prompt is built from `src/lib/fields.ts`, so it always matches what the app stores.
- **The model must quote its source** (`source_snippet`, `page`) for every value, and must return `null` rather than guess.
- **Every answer is parsed with Zod** (`src/lib/extraction/schema.ts`). Invalid JSON or a wrong shape gets one retry; if it fails again the document is marked failed and **nothing is saved** — no half-valid data.
- **Deterministic checks then flag doubtful values** (`normalize.ts`, `interpret.ts`):
  - the number must actually appear in the quoted text (catches invented values);
  - ISO 6346 check digit on container numbers (catches a single misread digit that the model's own confidence misses);
  - 8-digit ITC-HS codes, Incoterms 2020 rules, ISO 4217 currencies, real dates;
  - weights converted to kilograms (MT, LBS flagged);
  - European vs English number formats: `1.460` is ambiguous, so the document's own unambiguous figures (`7.650,00`) decide.
- **Model confidence is not calibrated**, so it is one signal among several. A field needs a person if confidence is below 85% [A], the value is missing, a check flagged it, or it is part of a failed cross-check (`src/lib/review.ts`).
- **Wrong slot detection:** the model reports what the document actually is; a packing list uploaded as an invoice is refused with a clear message.
- **Unreadable documents go to manual entry** with empty required fields. A failed extraction offers Retry or "Enter values manually".
- **No double runs:** a document is claimed atomically (`QUEUED|FAILED → EXTRACTING`), so two clicks or two tabs never extract twice.
- **Model call has a 50 s timeout** inside a 60 s function limit, so the function always finishes and records the result.
- **[A] Model:** `gemini-3.8-flash` by default, configurable with `GEMINI_MODEL`. Google lists it as the recommended Flash model for new projects; the 2.5 models are limited to existing users.
- **Provider and data use:** the brief requires an AI provider that does not train on client data. Google's paid Gemini API tier states that prompts and files are not used to improve its products; the free tier may be. The demo uses synthetic documents only; production must use the paid tier. [A] Gemini processing is not pinned to India.
- **Behind an interface** (`ExtractFn`), so the pipeline can be exercised with a fake model; that is how the invalid-JSON, outage and unreadable paths were checked.

## Cross-checks (the hard part)

- **Pure engine** (`src/lib/checks/engine.ts`): values in, results out. No database, no AI, so every rule is unit-tested (17 tests, including the brief's SHP-24811 case).
- **Exact decimal arithmetic** (`decimal.js`), never floats: 2,400 × 6.80 is exactly 16,320.00, and 0.1 + 0.2 equals 0.3.
- **Seven rules:**

  | Rule | Compares | Blocks export? |
  |---|---|---|
  | Invoice total | Σ (quantity × unit price) vs invoice total | yes |
  | Line amounts | each printed amount vs quantity × unit price | yes |
  | Quantities | invoice vs packing list, per unit | yes |
  | Packages | invoice, packing list and B/L | yes |
  | Gross weight | invoice, packing list and B/L, tolerance 0 kg [A] | yes |
  | Containers | packing list vs B/L, as sets | yes, if the packing list lists any |
  | Invoice reference | packing list's invoice number vs the invoice | no (extra) |

- **A missing document or value is `NOT_CHECKED`, never `PASS`,** and it blocks export. The message says exactly what is missing ("Waiting for documents: B/L not uploaded").
- **[A] The invoice may omit packages or weight**; the packing list and B/L must state them, and are then compared with each other.
- **[A] The invoice total is compared with the sum of lines only.** Freight, insurance or discounts printed as separate charges are not modelled in this build.
- **The engine never decides which document is right.** It reports the difference; a person corrects a misread value, or the manager accepts a genuine difference with a note.
- **Checks re-run inside the same transaction as every change** (`refreshShipment`), so stored results can never be stale.
- **An override only holds for the values it was given on.** Each result carries a signature of the compared values; if any value changes, the override is cleared.
- **Fields in a failed check need a person**, so the 45 kg mismatch highlights the weight on all three documents.
- **On screen, failures and waiting checks stay visible; passes fold away** into one line. Each mismatched value links to that field on its document.

## Review screen

- **Document on the left, decisions on the right**, in this order: cross-checks, fields, file details. The screen is used all day, so the work comes first.
- **Rows that need a person are full-size and coloured** (amber = uncertain, red = part of a failed cross-check) and show why: low confidence, missing, a specific flag, or the failed check. **Everything else is one compact line** with the source text in a tooltip.
- **One click per decision:** Confirm accepts the value; Edit opens an inline box (Enter saves, Esc cancels). A filter shows only fields that need a person.
- **Typed values go through the same validation as AI output**: a bad container check digit, a 6-digit HSN or an ambiguous `1.460` is refused with a message saying how to fix it. [A] Typed numbers are read English-style (comma = thousands).
- **Every correction keeps the AI's value** (`FieldCorrection`: old value, new value, who, when) and shows "AI read …" next to the corrected value. Typing a value the AI never found counts as manual entry, not a correction.
- **Missing line items or containers can be added, and invented ones removed** (with an inline "Remove this line?" confirmation).
- **Optimistic concurrency per field:** each save sends the `updatedAt` the user saw. If someone else changed the field first, the save is refused and the page refreshes, so nobody silently overwrites a colleague.
- **Every change re-runs the cross-checks in the same transaction**, so correcting the misread container immediately turns that check green.

## Edit history and audit log

- **Every important action writes an `AuditLog` row in the same transaction as the change**: shipment created, upload, extraction (success, unreadable or failure), manual entry, confirm, correct, enter, add or remove a row, approval withdrawn, override, approval, export, and **document downloads** (client prices are confidential, so we record who took a copy).
- **Entries are plain sentences** ("Priya Nair corrected container 1 on the bill of lading: MSKU7182845 → MSKU7182345"), generated from structured metadata by `describeAudit` (unit-tested).
- **Per shipment:** an Activity section on the workspace, for both roles. **Across shipments:** an Activity page for the manager only, filterable by type and shipment code.
- **Per field:** a History toggle lists every change (old → new, who, when). This is the raw data for the accuracy report per field and supplier, which is the next thing to build.
- [A] Opening a document in the viewer is not logged (it would flood the log); downloading a copy is.

## Approval and export

- **One pure gate** (`src/lib/export/gate.ts`, unit-tested) decides three things: the status shown everywhere, whether the manager may approve, and whether the server will export. They can never disagree.
- **Export requires:** all three documents extracted (or entered manually); no field that needs a person left unconfirmed; every blocking cross-check passed or accepted by the manager; and manager approval.
- **Enforced on the server, in the export transaction.** The export button being disabled is a convenience. Calling `POST /api/shipments/[id]/export` directly while anything is open returns 409 with the reasons.
- **Manager approval is of a specific version.** The approve call sends the `version` the manager saw; if anything changed meanwhile it is refused. Any later data change withdraws the approval automatically and logs it.
- **Accepting a failed check needs a written reason** (10+ characters) recorded with the manager's name, shown on the check and in the audit log. Only a real `FAIL` can be accepted; a check that could not run (`NOT_CHECKED`) never can.
- **[A] Who exports:** after approval, either role may export. Only the manager approves and accepts differences.
- **CSV layout is defined in one place** (`src/lib/export/csv.ts`). [A] The filing software's real import layout is not given, so this build uses one row per invoice line with shipment-level values repeated; matching the real layout means editing the `COLUMNS` list.
- **[A] Packages and gross weight are exported as on the B/L**, the carrier's document; net weight from the packing list.
- **CSV details:** RFC 4180 quoting, CRLF line endings, a UTF-8 BOM so Excel shows names like "Västra Frölunda" correctly, and **CSV-injection protection** (cells starting with `=`, `+`, `-` or `@` are prefixed so Excel does not run them as formulas).
- **Each export stores the exact file produced** (`Export.content`), so it can be downloaded again and audited even after data changes. Exporting locks the shipment.
